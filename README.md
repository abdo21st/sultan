# منظومة سلطان

تطبيق لإدارة طلبات الأثاث بين المعارض والمصانع، ومتابعة مراحل التنفيذ والمدفوعات والإشعارات. يتكون من واجهة Next.js وخدمات API وقاعدة PostgreSQL، وتُدار بنية قاعدة البيانات عبر Prisma Migrate.

## المتطلبات

- Node.js 22، أو إصدار يطابق الحد الأدنى المعلن في `package.json`.
- PostgreSQL 15 أو أحدث.
- npm؛ ملف `package-lock.json` هو ملف القفل المعتمد.

## الإعداد المحلي

1. أنشئ ملف `.env.local` انطلاقًا من `.env.example`، واملأ القيم محليًا. لا تضع الأسرار في Git.
2. ثبّت الحزم وشغّل الفحص المالي للقراءة فقط:

   ```bash
   npm ci
   npm run db:financial-preflight
   ```

   يعرض الفحص أعدادًا مجمعة بلا بيانات شخصية. يعيد رمز خروج غير صفري إذا وجد مبالغ غير صالحة أو فروقًا بين رصيد الطلب وسجل الدفعات.

3. لقاعدة بيانات جديدة، طبّق الترحيلات ثم أنشئ الحساب والمنشآت الأولية:

   ```bash
   npm run db:migrate:deploy
   npm run db:seed
   ```

   يتطلب إنشاء المدير لأول مرة `INITIAL_ADMIN_PASSWORD` بطول 12 محرفًا على الأقل وبحد أقصى 72 بايت UTF-8. يلزم الحساب الجديد تغيير كلمة المرور عند أول دخول. لا يعيد seed تعيين كلمة مرور حساب موجود أو حالة تغييرها أو رقم جلساته، ويضيف المنشآت الافتراضية مرة واحدة.

4. شغّل التطبيق:

   ```bash
   npm run dev
   ```

## قاعدة بيانات موجودة

### كلمات المرور وروابط المشاركة

الحسابات التي ينشئها المدير، والحساب الذي يعيد تعيين كلمة مروره، تتوقف عند صفحة تغيير كلمة المرور الأولية قبل أي عملية تشغيلية. تغيير كلمة المرور يلغي جميع جلسات الحساب السابقة؛ كما يلغي تعديل الدور أو نطاق المنشأة الجلسات القديمة. تُراجع الجلسات من قاعدة البيانات عند فتح الصفحات وطلبات الخادم. تتوقف جلسة بث الإشعارات الملغاة عند الفحص التالي خلال 15 ثانية.

عند ترقية حساب مدير قديم لا تفترض أن كلمة مروره ما زالت أولية. أداة `scripts/enroll-initial-admin.ts` تقرأ JSON عبر stdin يحوي `username` و`initialPassword`، وتقارن التجزئة قبل إلزام التغيير وإلغاء الجلسات. تحافظ على كلمة مرور غيّرها صاحب الحساب، وتقبل إعادة التشغيل بأمان. شغّلها داخل صورة الترحيلات عبر `node --import tsx scripts/enroll-initial-admin.ts`، بتمرير الإدخال من ملف محمي أو مدير أسرار دون وضعه في وسيطات الأمر أو سجل الطرفية.

تحتاج مشاركة الطلب صلاحيات `orders:view` و`orders:view_financials` و`orders:share` مع نطاق المنشأة والحالة. تحتاج عملية إلغاء الروابط `orders:revoke_shares`. تُتاح المشاركة افتراضياً للمدير والمشرف والمحاسب، والإلغاء للمدير والمشرف. يسجل النظام مصدر الإصدار ووقت الانتهاء وبصمة الرمز دون حفظ الرمز نفسه في سجل التدقيق. يؤدي الإلغاء من صفحة الطلب إلى إبطال كل الروابط ورموز QR السابقة وصورها فور الطلب التالي، بما فيها الروابط القديمة الصالحة قبل الترقية. لا يسحب الملفات التي سبق تنزيلها. يمكن إصدار رابط جديد صالح لسبعة أيام بعد الإلغاء.

الترحيل `20261021000000_session_and_share_revocation` إضافي ولا يعيد ضبط كلمات مرور أو أرصدة الحسابات الموجودة. يؤدي نشر الإصدار إلى طلب الدخول مجدداً للجلسات التي صدرت قبل إضافة رقم الجلسة.

قاعدة بيانات كانت تعمل قبل إضافة Prisma Migrate تحتاج تسجيل خط أساس قبل نشر الترحيل الجديد. أنشئ نسخة مشفرة بالطريقة أدناه، وشغّل `npm run db:financial-preflight` أولًا. بعد التحقق من أن مخطط القاعدة يطابق ترحيل خط الأساس `20261020000000_initial_baseline`، سجّل الخط الأساس مرة واحدة:

```bash
npx prisma migrate resolve --applied 20261020000000_initial_baseline
npm run db:migrate:deploy
```

لا تسجّل الخط الأساس على قاعدة جديدة أو على مخطط غير مطابق. إذا أوقف الفحص المالي الترحيل، عالج الفروق وراجعها قبل إعادة المحاولة. لا تُجرِ هذا الإجراء على الإنتاج قبل أخذ نسخة احتياطية والتحقق من إمكانية استعادتها.

## الطلبات المحفوظة عند انقطاع الشبكة

بعد فتح نموذج الطلب أثناء الاتصال، يحفظ الطلب غير المتصل وصوره على الجهاز، بمعرّف ثابت يمنع إنشاء نسخة ثانية عند إعادة الإرسال. يعرض شريط المزامنة عدد الطلبات المحلية، وسبب الفشل وزر إعادة المحاولة، ويحفظ هذه الحالة بعد إعادة فتح الصفحة. عند انتهاء الجلسة يوقف الإرسال التلقائي ويطلب تسجيل الدخول؛ تبقى الطلبات والصور محفوظة حتى نجاح إرسالها.

يحفظ النموذج قائمة منشآت واحدة تحتوي المعرّف والاسم والنوع فقط، دون العناوين أو أرقام الاتصال أو أسرار الجلسة. ترتبط ببصمة الحساب والدور والمنشأة وإصدار الجلسة والصلاحيات، وتنتهي بعد 24 ساعة. تُرفض القائمة القديمة أو المختلفة، وتُمسح عند الخروج أو رفض الوصول. توجد القائمة في قاعدة متصفح منفصلة للحفاظ على إصدار طابور الطلبات السابق وإمكان فتحه عند الرجوع إلى الواجهة السابقة. لا تغني القائمة المحفوظة عن تحقق الخادم من الصلاحيات عند الإرسال. عند إعادة تشغيل المتصفح بالكامل دون اتصال تظهر صفحة الانتظار؛ يعود التطبيق للمزامنة عند عودة الشبكة.

تغطي مجموعة `@offline_images` إعادة تشغيل المتصفح مع صورة محفوظة، وفشل الرفع وإعادة المحاولة، وانتهاء الجلسة، وفقدان رد النجاح، وحدود قائمة المنشآت، وبقاء صورة الطابور السابق مع إمكان فتحه بإصدار التخزين السابق بعد تحديث الواجهة. يفحص المشغّل عدد الطلبات والمفاتيح والصور وسجلات الإنشاء مستقلاً عن نتيجة الواجهة. اختبارات Chrome، بما فيها العرض بحجم هاتف، لا تستبدل قبول هاتف فعلي على بيئة الاختبار.

## تشغيل Docker المعزول

يتطلب `docker-compose.isolated.yml` ملف `.env` محليًا يحتوي `DB_PASSWORD` وبقية إعدادات التطبيق المطلوبة. يمكنك إنشاءه من `.env.example` ثم ضبط `DATABASE_URL` و`DIRECT_URL` على عنوان الخدمة `sultan-db` عند استخدام Compose. ينشئ Compose شبكة داخلية وقاعدة PostgreSQL، وينفذ الترحيلات في خدمة مستقلة قبل تشغيل التطبيق. منفذ قاعدة البيانات متاح محليًا على `127.0.0.1:5433` فقط.

```bash
docker compose -f docker-compose.isolated.yml up --build -d
```

لا تستخدم `docker compose down -v` إلا إذا كنت تقصد حذف بيانات قاعدة Docker. نقطة `/api/health` تفحص اتصال قاعدة البيانات ولا تعرض تفاصيلها.

## تشغيل Docker على الخادم السحابي

يستخدم `docker-compose.cloud.yml` قاعدة PostgreSQL مستقلة بحجم دائم غير منشور على الإنترنت، ويربط التطبيق على `127.0.0.1:3005` ليخدمه Nginx مع HTTPS. يتطلب ملف `.env` على الخادم قيمًا عشوائية خاصة لـ`DB_PASSWORD` و`AUTH_SECRET` و`CRON_SECRET`، وكلمة مرور أول مدير عند التهيئة الأولى. لا ترفع ملف الأسرار إلى Git أو إلى سياق البناء. ينشئ هذا الإعداد قاعدة جديدة فارغة؛ لا تستخدمه لاستبدال قاعدة تشغيلية أو ترحيل بياناتها.

```bash
flock -n /run/lock/sultan-backup.lock docker compose -f docker-compose.cloud.yml up --build -d sultan-app
flock -n /run/lock/sultan-backup.lock docker compose -f docker-compose.cloud.yml run --rm sultan-migrate npm run db:seed
docker compose -f docker-compose.cloud.yml ps
curl --fail https://sultan.mtapp.ly/api/health
```

تحقق من النسخ الاحتياطي المشفر واستعادة نسخة مستقلة قبل تخزين بيانات تشغيلية. لا يُنشر منفذ PostgreSQL على واجهة الخادم.

ملف `config/nginx/sultan.mtapp.ly.conf` يضبط النطاق وHTTPS وحد رفع 50 ميغابايت، بما يغطي عشر صور بحد 4.5 ميغابايت للصورة. يتطلب شهادة Let's Encrypt صالحة بالمسارات المذكورة. بعد تثبيت ملف النطاق في Nginx، نفذ `nginx -t` ثم أعد تحميل Nginx. يستخدم النشر والنسخ اليومي القفل نفسه أعلاه لمنع تزامن تحديث التطبيق مع التقاط النسخة المتسقة.

### تخزين الصور في النسخة السحابية

يستخدم Compose السحابي `ORDER_IMAGE_STORAGE=local` وحجم Docker الدائم `sultan-production-images` المركب في `/app/storage/order-images`. لا يحتاج هذا المسار إلى رمز Vercel. يحفظ التطبيق معرفات ملفات عشوائية، ويعرض الصور عبر `/api/orders/:id/images/:index` بعد التحقق من صلاحية المستخدم ونطاق المنشأة أو رمز المشاركة. لا يوجد مسار عام مباشر للحجم. تعمل عملية التطبيق بحساب غير root، وتُنشأ الصور بصلاحيات `0600`.

تظل مراجع Vercel القديمة مدعومة عند وجود رموز مخازنها، أما الرفع الجديد في النسخة السحابية فيستخدم الحجم المحلي. طابور الحذف الدائم يعالج النوعين ويتحقق من عدم بقاء مرجع إلى الصورة قبل حذفها.

لإعادة الاختبارات على خادم Linux، ابنِ هدف `verification` ثم شغّل المشغّل المعزول. ينشئ حاوية PostgreSQL مؤقتة ومنفذاً محلياً مستقلاً، ويجري اختبارات الوحدة والمتصفح والاستعادة دون استخدام قاعدة التطبيق المنشور:

```bash
docker build --target verification -t sultan-plan-verification:20261020 .
sh scripts/verify-cloud-build.sh sultan-plan-verification:20261020
```

### نسخة متسقة من قاعدة البيانات والصور

يتطلب الأمر التالي Node.js 22.18 أو أحدث وDocker وأداة `tar` على مضيف Linux، مع `DB_BACKUP_ENCRYPTION_KEY` في ملف البيئة المحمي. يوقف مؤقتاً تنفيذ حاوية سلطان أثناء التقاط قاعدة البيانات وحجم الصور، ثم يعيد تشغيل تنفيذها حتى لو فشل النسخ. قد تتأخر الطلبات لبضع ثوانٍ أثناء الالتقاط. لا يوقف خدمات المشاريع الأخرى. يتضمن المجلد الناتج ملفي AES-256-GCM مشفرين وبصمتي SHA-256 وبيانات وصفية، وتُفحص مصادقة الملفين وفهارس الأرشيف قبل كتابة علامة `VERIFIED`:

```bash
node scripts/cloud-backup.mjs create
node scripts/cloud-backup.mjs verify --directory /var/backups/sultan-production/اسم-النسخة --container sultan-production-sultan-db-1
```

انقل المجلد الكامل إلى وجهة خارج الخادم، واحفظ المفتاح في مكان خاص منفصل. يمكن تمرير ملف مفتاح منفصل عبر `--key-file` دون عرضه. يحتفظ الأمر افتراضياً بآخر 30 نسخة مكتملة ومتحقق منها على الخادم؛ يمكن ضبط العدد عبر `--keep` بين 1 و365. لا يحذف مجلداً غير معروف أو نسخة ناقصة. لا تنقل أداة الخادم الملفات خارجه تلقائياً.

تتضمن `config/systemd` مؤقت نسخ يومياً قرابة 03:15 بتوقيت ليبيا ومؤقت إعادة محاولة حذف الصور قرابة 04:15. ثبت ملفات `sultan-*.service` و`sultan-*.timer` في `/etc/systemd/system` ثم نفذ `systemctl daemon-reload` و`systemctl enable --now sultan-backup.timer sultan-image-cleanup.timer`. تحقق من نتيجة تشغيل الخدمتين فعلياً؛ ظهور المؤقت وحده لا يثبت نجاح النسخ أو الحذف. تتطلب وجهة النسخ الخارجية آلية نقل مستقلة واختبار استعادة من النسخة المنقولة.

لنقل أحدث لقطة متحقق منها إلى جهاز Windows عبر اتصال SSH المعد مسبقاً باسم `nawat-server`، شغّل `./scripts/pull-cloud-backup.ps1` من PowerShell 7. ينقل الملفات المشفرة فقط إلى `local-backups/cloud`، ويفحص SHA-256 قبل اعتماد المجلد، ويحتفظ افتراضياً بآخر 30 نسخة محلية متحقق منها. المفتاح لا يُنقل مع النسخة. يمكن تحديد الوجهة عبر `-Destination` وعدد النسخ عبر `-Keep`. يحتاج النقل المجدول أن يكون الجهاز قيد التشغيل ومتصلًا بالإنترنت؛ اعتمد وجهة خارجية تعمل دائماً إذا كانت النسخ اليومية دون انقطاع مطلوبة.

الوجهة المعتمدة هي مخزن خارجي يعمل دائماً ومتوافق مع S3. نموذج حقوله العامة في `config/offsite-backup.env.example`؛ ملف القيم السرية على الخادم هو `/opt/sultan-production/.env.backup-offsite`، ملك `root` وبصلاحية `600`، ومستبعد من Git وصورة Docker. يضبط المشغل عنوان HTTPS والمنطقة واسم الحاوية ومفتاح الوصول وسره والبادئة. هذه المرحلة تجهز الإعداد فقط؛ النقل الخارجي المجدول غير مفعّل إلى أن تُضبط الوجهة ويُختبر الرفع والاستعادة منها فعلياً. لا تضع مفتاح فك تشفير النسخ في هذا الملف أو في مخزن النسخ.

أداة `scripts/backup-offsite.mjs` تنقل النسخ المشفرة بواسطة صورة Rclone مثبتة ببصمتها، دون تركيب مقبس Docker أو تمرير مفتاح النسخ إلى حاوية النقل. المرجع: [تشغيل Rclone في Docker](https://rclone.org/install/#install-with-docker) و[إعداد S3](https://rclone.org/s3/). تبقى مفاتيح الوجهة في ملف مؤقت خاص يُحذف بعد التشغيل، ولا تُطبع قيم الإعداد أو سجلات النقل. تُستخدم HTTPS مع التحقق من الشهادة، ولا تُنشئ الأداة حاوية S3 أو تحذف ملفات الوجهة. تحتاج هوية الوجهة إلى قراءة وكتابة كائنات النسخ، ويمكن تقييدها بالبادئة المعتمدة دون صلاحية حذفها.

تفحص الأداة النسخة المحلية وتوثيق AES-GCM قبل الرفع، وتعيد تنزيل كل ملف وتطابق SHA-256 وتوثيق الأرشيفين. تنشر `OFFSITE-VERIFIED.json` أخيراً؛ يربط توقيع HMAC اسم اللقطة وبصمات الملفات الأربعة، بمفتاح مشتق عبر HKDF من مفتاح النسخ الموجود خارج الوجهة. يمنع ذلك تبديل ملف البيان أو خلط أجزاء من لقطات مختلفة دون كشفه. لا تُرسل مفتاح النسخ أو مفتاح التوقيع إلى S3. إعادة الرفع لا تستبدل كائناً مختلفاً، ويحتفظ سجل محلي خاص بإيصالات النقل المكتمل. يُنزّل الاسترجاع التوقيع ويفحصه قبل ملفات البيانات ثم يفحص توثيقها. هذه الحماية لا تغني عن قيود الوصول والاحتفاظ لدى مزود التخزين.

بعد إعداد الملف، نفّذ فحص الإعداد ثم قبول وجهة واحدة قبل تفعيل المؤقت:

```bash
node scripts/backup-offsite.mjs check-config
flock -n /run/lock/sultan-backup.lock node scripts/backup-offsite.mjs upload-pending
node scripts/backup-offsite.mjs download --snapshot <verified-snapshot-name> --destination <new-private-directory>
```

استخدم الملفات المنزلة لاختبار استعادة القاعدة والصور في موارد مؤقتة وفق الخطوات أدناه. بعد نجاح الرفع والاستعادة الفعليين تُثبت وحدتا `config/systemd/sultan-offsite-backup.service` و`config/systemd/sultan-offsite-backup.timer` ثم يُفعّل المؤقت. يفحص النقل اللقطات المحتفظ بها، ويرسل الأحدث أولاً ثم ما لم يملك إيصالاً صالحاً؛ لا يعيد إرسال المنجز إلى الوجهة نفسها. توقيته اليومي 02:45 UTC، ويعيد فحص المعلّق عند إقلاع الخادم بعد عشر دقائق. لا يكفي نجاح فحص الإعداد أو قبول S3 التجريبي لإعلان قبول المزود الحقيقي. المؤقت الخارجي غير مفعّل حالياً.

`npm run test:offsite` يفحص إعدادات الوجهة والتوقيع وحدود الملفات، ويضيف `--offsite-test` إلى اختبار `cloud-storage-backup-acceptance.mjs` مخزن Adobe S3Mock مؤقتاً على loopback لإثبات النقل والتنزيل والاستعادة. استثناء HTTP مخصص لهذا العنوان الاختباري الصريح فقط؛ لا يعطّل التحقق من TLS لوجهة خارجية. [توثيق S3Mock](https://github.com/adobe/S3Mock) يوضح أنه مخزن للاختبار ولا يتحقق من كل جوانب المصادقة؛ قبول بيانات اعتماد المزود الحقيقي يبقى خطوة مستقلة.

نجح قبول الأداة على Linux: سبعة اختبارات وحدات، ورفع اللقطة نفسها مرتين، وتجاوز المنجز بإيصال مطابق، وتنزيل نسخة مطابقة بايتاً ببايت، ورفض بيان معدّل قبل تنزيل قاعدة البيانات. استُعيدت القاعدة والصورة من الملفات المنزلة من S3Mock، ثم أُعيد إنشاء التطبيق ودخل الحساب وقرأ الصورة الخاصة بنجاح؛ طلب واحد ودفعة واحدة وصورة واحدة دون فروق في دفتر التحصيل. كانت بيانات ومفاتيح الاختبار اصطناعية، ولم تُستخدم إعدادات وجهة المالك الحقيقية. صورة Rclone مثبتة ببصمة SHA-256، وفُحص تشغيل الإصدار 1.75.2؛ تضبط الأداة صلاحيات الملفات محلياً، ولا تعتمد خيار `--umask` غير المدعوم في أمر النقل.

### إدارة سلطان عبر حساب SSH محدود

ثُبت حساب `sultan-operator` ومفتاح مستقل له؛ المفتاح الخاص محفوظ بصلاحيات المستخدم وحده على جهاز المشغل، ونُسخ المفتاح العام فقط إلى الخادم. اسم الاتصال المحلي هو `sultan-operator-server`. يتيح مدخل SSH أربعة أوامر ثابتة: `status` و`health` و`restart` و`backup`. مثلاً: `ssh sultan-operator-server health`. لا يملك الحساب عضوية Docker أو sudo عاماً، ولا يمكنه قراءة ملف البيئة أو تعديل غلاف العمليات. يملك المدير وحده ملفات الحساب والمفتاح العام وقواعد sudo والمدخل الإجباري.

تفرض `config/ssh/70-sultan-operator.conf` المصادقة بالمفتاح ومدخل أوامر إلزامياً، وتمنع TTY وتمرير الاتصالات وملف تشغيل المستخدم. يحدد `scripts/sultan-operate.py` أسماء حاويتي سلطان والخدمة ومسار الصحة ثابتة، ويشغّلها ببيئة محددة دون إدخال مسارات أو معاملات Docker من العميل. تحترم إعادة التشغيل قفل النسخ والنشر وترفض التطبيق الموقوف مؤقتاً؛ تستخدم النسخ الاحتياطي الخدمة القائمة. لا يعرض المدخل سجلات التطبيق أو مخرجات فشل الأوامر التي قد تحتوي أسراراً. المرجع: [إعدادات OpenSSH الرسمية](https://man.openbsd.org/sshd_config).

ثبت القبول بدخول SSH منفصل: الحالة والصحة والنسخ الاحتياطي نجحت، ورُفضت خمسة أوامر غير مسموحة، وتمرير TCP، وقراءة البيئة وتعديل الغلاف وsudo العام والوصول المباشر إلى Docker. نجح 11 اختبار وحدة للغلاف؛ إعادة التشغيل تستهدف حاوية التطبيق وحدها وتغطي الاختبارات قفل النسخ والتوقف المؤقت ومسار النجاح. يُعاد تثبيت الملفات المملوكة للمدير من `scripts/install-sultan-operator.sh <public-key-file>`؛ يحمي المثبّت الحسابات الموجودة غير التابعة لهذا الإعداد ويفحص sudo وSSH قبل إعادة تحميل إعداد SSH.

سياسة root على الخادم المشترك ما زالت بانتظار قرار المالك. الملف `config/ssh/80-sultan-root-key-only.conf` مقترح جاهز للمفاتيح فقط؛ **غير مثبّت**. نجح `python3 scripts/preview-root-ssh.py` في فحصه دون تغيير الإعداد الحي، وأثبت بقاء سياسة حساب المشغل وحساب آخر كما هي. تدوير كلمة root وإيقاف دخولها بكلمة مرور خطوة مستقلة بعد تنسيق اعتمادها؛ هذا الحساب المحدود وحده لا يغلق بند اعتمادات SSH القديمة.

### قبول الهاتف الحقيقي

تعمل بيئة اختبار مستقلة على `https://sultan-qa.mtapp.ly` من صورة التطبيق `102a78b`، بقاعدة وحجم صور وحساب مصطنع منفصل، ومن دون منفذ PostgreSQL عام. حُدد استهلاك الموارد، وأضيف حد محاولات الدخول ومنع الفهرسة. يعرض شريط التطبيق اسم «سلطان — بيئة اختبار الهاتف»، واسم التطبيق عند إضافته للشاشة «سلطان اختبار». ملفات إعدادها في `config/mobile-acceptance.compose.yml` و`config/nginx/sultan-mobile-acceptance.conf`، وإعدادها الأول عبر `scripts/install-mobile-acceptance.sh`. ملفات القيم السرية في `/opt/sultan-mobile-acceptance` بصلاحيات خاصة؛ لا يطبع المثبّت بيانات الدخول ولا يعيد تهيئة بيئة موجودة.

بيانات الدخول الاختبارية على جهاز المشغل في `C:/Users/phabd/.codex/private-deployments/sultan-mobile-acceptance-20261021.json` بصلاحيات المستخدم وحده. هذه ليست بيانات حساب الإنتاج. نجح فحص HTTPS والدخول بدور مدير المنشأة وفتح نموذج الطلب والتحقق من الصورة الخاصة، ورفض المجهول لها. لا يُعد هذا قبولاً لهاتف حقيقي؛ لا يوجد هاتف Android متصل بأدوات الفحص حالياً.

نفّذ التجربة التالية من متصفح هاتف Android أو iPhone عادي، أو من نسخة الاختبار المضافة إلى شاشته الرئيسية، ببيانات مصطنعة فقط:

1. افتح نطاق الاختبار وسجل الدخول، ثم افتح «إنشاء طلب جديد» أثناء الاتصال حتى تظهر قائمة المصنع والمعرض.
2. افصل اتصال الهاتف، ثم أنشئ طلباً باسم مميز مثل «قبول الهاتف 21»، ورقم اختباري `0910000000` ووصف تجريبي وموعد مستقبلي وإجمالي `100` ومدفوع `0`. أرفق صورة لورقة فارغة. تحقق من رسالة «تم حفظ الطلب محلياً».
3. أغلق المتصفح أو نسخة الاختبار بالكامل وأعد فتح رابطها وهي دون اتصال. ينبغي أن تظهر صفحة «أنت غير متصل بالإنترنت» و«بانتظار عودة الاتصال».
4. أعد الاتصال وافتح التطبيق؛ انتظر رسالة المزامنة أو استخدم زر الطلبات المحفوظة لإعادة المحاولة إذا ظهر فشل. تحقق من ظهور الطلب مرة واحدة وصورته الصحيحة، ثم أعد فتحه أو تحديث الصفحة للتأكد من عدم تكراره.
5. أبلغ القبول بنوع الهاتف والمتصفح واسم طلب الاختبار ونتيجة الصورة والتكرار. لا ترسل كلمة المرور. يفحص المشغل سجل الطلب والحركة والصورة في قاعدة الاختبار مستقلاً بعد التجربة؛ لا يُسجل بند الهاتف مكتملاً قبل ذلك.

سجلا وصول وأخطاء هذه البيئة منفصلان عن بقية المشاريع، ولا تسجل Nginx محتوى الطلب أو كلمة المرور. تُستخدم سجلات الوصول الخاصة بها لتأكيد متصفح الهاتف عند مراجعة نتيجة القبول، دون نشر عنوان المستخدم أو تفاصيل اتصاله. تتضمن بيانات التهيئة طلباً واحداً وصورة تجريبية دون دفعات؛ ليست بيانات أعمال فعلية.

لاستعادة الصور، تقبل الأداة حجماً جديداً فقط ينتهي بـ`_restore_test` وتفحص أسماء أعضاء الأرشيف قبل الاستخراج. استعد قاعدة البيانات إلى قاعدة اختبار جديدة باستخدام أداة النسخ المشفر السابقة، ثم شغّل التطبيق على القاعدة والحجم المستعادين للتحقق من الطلبات والصور:

```bash
node scripts/cloud-backup.mjs restore-images --directory /path/to/copied-snapshot --container sultan-postgres-db --target-volume sultan_images_restore_test --key-file /private/backup-key.env
npm run db:backup:encrypted -- restore --file /path/to/copied-snapshot/database.dump.aesgcm --container sultan-postgres-db --target-db sultan_cloud_restore_test --apply --start-app
```

لاختبار الاستعادة الشاملة للصور والبيانات دون لمس الإنتاج، يشغّل الأمر التالي مشروع Compose مؤقتاً بمفاتيح وبيانات اصطناعية: يرفض الوصول المجهول، ويقرأ الصورة بعد الدخول، ويأخذ لقطة متسقة، ويرفض تعديل النص المشفر حتى مع تغيير بصمته، ويستعيد قاعدة وحجم صور مستقلين، ثم يعيد إنشاء التطبيق ويقارن بايتات الصورة والدفتر المالي. يحذف موارده المؤقتة عند الانتهاء:

```bash
node scripts/cloud-storage-backup-acceptance.mjs sultan-private-candidate:20261020 sultan-production-sultan-migrate
```

## متغيرات البيئة

- `DATABASE_URL`: اتصال التطبيق بقاعدة البيانات.
- `DIRECT_URL`: اتصال مباشر لأوامر Prisma؛ عند غيابه يستخدم `DATABASE_URL`.
- `AUTH_SECRET`: سر المصادقة، ويجب أن يكون عشوائيًا وطويلًا (32 محرفًا أو أكثر).
- `AUTH_URL`: عنوان التطبيق العام مع HTTPS في الإنتاج؛ يستخدم لإنشاء روابط QR والمشاركة.
- `ORDER_SHARE_SECRET`: سر مستقل اختياري لروابط مشاركة الطلبات؛ عند غيابه يستخدم سر المصادقة.
- `CRON_SECRET`: سر عشوائي طويل مطلوب لتأمين مهام التنظيف والصيانة المجدولة.
- `INITIAL_ADMIN_USERNAME` و`INITIAL_ADMIN_PASSWORD`: مطلوبان لإنشاء المدير عند أول seed فقط.
- `WHATSAPP_API_ALLOWED_HOSTS`: قائمة أسماء نطاقات دقيقة مفصولة بفواصل لمزوّد WhatsApp. لا يرسل التطبيق إلى عنوان غير HTTPS أو خارج هذه القائمة. عيّنها قبل حفظ عنوان المزوّد.
- رابط مزود WhatsApp ومفتاحه يُحفظان من صفحة الإعدادات؛ لا يعيد التطبيق المفتاح السري في واجهة API. يتطلب الإرسال التلقائي صلاحية `whatsapp:send`، ويسجل المحاولات والنتائج، ويحد الإرسال إلى 10 محاولات لكل مستخدم في الدقيقة.
- `BLOB_READ_WRITE_TOKEN`: رمز مخزن Vercel Blob خاص. الرفع الجديد خاص، وتُعرض الصور من خلال مسار يتحقق من الجلسة أو رابط المشاركة.
- `ORDER_IMAGE_STORAGE`: المزود `vercel` افتراضياً أو `local` للتخزين الخاص الدائم. ملف Compose السحابي يضبطه على `local`.
- `ORDER_IMAGE_STORAGE_DIR`: مجلد مطلق خارج `public` و`.next/static` عند استخدام التخزين المحلي؛ يجب نسخه مع قاعدة البيانات.
- `BLOB_LEGACY_PUBLIC_READ_WRITE_TOKEN`: رمز اختياري للمخزن العام القديم عند استخدام مخزن منفصل؛ يمكّن حذف الصور العامة بعد نقلها أو إزالتها من الطلب.
- `DB_BACKUP_ENCRYPTION_KEY`: مفتاح base64 يمثل 32 بايتًا عشوائيًا، يُحفظ في مدير أسرار منفصل عن النسخ الاحتياطية.

يجب تزويد PostgreSQL بعنوان SSL وشهادات موثوقة بحسب مزود قاعدة البيانات. التطبيق لا يعطل التحقق من شهادة TLS.

إذا سبق إدخال أي سر أو بيانات اتصال إلى مستودع Git، فدوّرها لدى مزود الخدمة حتى بعد حذفها من الملفات الحالية؛ حذفها من النسخة الحالية لا يزيلها من سجل Git السابق.

### نقل الصور القديمة

أنشئ مخزن Blob خاصًا، واضبط رمزه في `BLOB_READ_WRITE_TOKEN`، ثم اعرض عدد الصور القديمة القابلة للنقل:

قبل نقل الصور التشغيلية، اختبر الرمز والمخزن الحقيقيين عبر `npm run test:blob:provider`. يرفع الأمر صورة PNG اصطناعية صغيرة إلى المسار الخاص، يقرأ بياناتها الوصفية، يحذفها، ثم يتحقق من اختفائها. لا يعرض الرابط أو الرمز في المخرجات.

```bash
npm run blob:secure-existing-images
```

بعد مراجعة العدد وأخذ نسخة احتياطية من قاعدة البيانات، شغّل النقل:

```bash
npm run blob:secure-existing-images -- --apply
```

ينقل الأمر روابط Vercel Blob العامة المدعومة ويحدّث سجل الطلب بشرط ألا تكون قائمة الصور قد تغيرت أثناء النقل، ثم يضيف الرابط العام القديم إلى قائمة حذف قابلة لإعادة المحاولة. الصور التي ينتمي عنوانها لمزود آخر تُعرض كغير مدعومة ولا تُحذف. يلزم ضبط رمز المخزن العام القديم إذا كان منفصلًا عن المخزن الخاص. تعمل إعادة المحاولة عبر مهمة يومية محمية بـ`CRON_SECRET`.

إذا فشل حفظ الطلب أو تعديله بعد رفع صور جديدة، يضيف التطبيق روابط الصور غير المرتبطة إلى طابور الحذف ويحاول حذفها فورًا. إذا تعذر حذفها، تبقى في الطابور لإعادة المحاولة بدل فقدان سجل التنظيف.

## فحوص التطوير

### تصحيح الحركات المالية بقيد عكسي

نُشر الإصدار `e6f3a63` على `https://sultan.mtapp.ly` مع قيد عكسي كامل مرتبط بالحركة الأصلية، والسبب وهوية المستخدم ومفتاح UUID ثابت لإعادة المحاولة. اعتمد مالك المشروع بقاء حالة التسليم عند عكس دفعة طلب مكتمل: يُصحّح المحصل والمتبقي، ويظهر الرصيد في قائمة الطلبات المستحقة، ويمكن تحصيله لاحقاً دون إعادة تنفيذ التسليم. اعتمد أيضاً بدء العمل بقاعدة جديدة؛ لا يوجد نقل لأرصدة تشغيلية قديمة ضمن هذا الإطلاق.

يحتاج المسار `POST /api/transactions/{id}/reverse` صلاحية `transactions:reverse` و`transactions:view`، ومع دفعة الطلب صلاحية `orders:view_financials` ونطاق المنشأة. تُمنح صلاحية العكس افتراضياً للمدير فقط ويمكن تفويضها بدور مخصص. يقبل الطلب `reason` و`idempotencyKey`، ويحسب الخادم القيمة من الحركة الأصلية؛ لا يقبل قيمة مالية بديلة من العميل.

يبقى الأصل دون تعديل، ويُضاف قيد سالب من النوع والتصنيف والمنشأة والطلب نفسها، ليتوازن صافي الإيراد أو المصروف والمجاميع والتقارير. لا يسمح بعكس الحركة نفسها مرتين أو بعكس قيد عكسي. إن كانت الحركة دفعة طلب، يتناقص المحصل ويزداد المتبقي بالقيمة نفسها داخل معاملة واحدة مع سجل التدقيق. تكرار المفتاح والسبب يعيد القيد نفسه دون إعادة التعديل؛ استخدام المفتاح لطلب مختلف يُرفض.

الترحيل `20261021000100_transaction_reversals` يمنع تعديل حقائق الحركات المسجلة، ويمنع القيد السالب دون أصل وسبب ومطابقة تامة. تتحقق قيود مؤجلة في PostgreSQL عند إنهاء المعاملة من تطابق صافي دفتر التحصيل مع المحصل في الطلب؛ تتوقف الترقية عند وجود فرق سابق بدلاً من تعديل الأرصدة تلقائياً. آلية القيود موثقة في [مرجع PostgreSQL](https://www.postgresql.org/docs/15/sql-createtrigger.html).

تعمل اختبارات المتصفح على مرحلتين في قاعدة مؤقتة: القبول السابق أولاً، ثم واجهة العكس وصلاحياته والتكرار والتزامن والمجاميع. يفحص المشغل رفض الكتابات غير المتسقة مباشرة، ثم يجرب المسح الشامل والتراجع عنه داخل المعاملة ليتأكد من عدم تعطيل إجراءات التصفير المصرح بها. يشمل اختبار الاستعادة قيداً أصلياً وتصحيحه وقيداً بديلاً وسجل تدقيق؛ يقارن بصمات السجلات قبل النسخ وبعد الاستعادة مع مصادقة AES-GCM مستقلة.

يشمل القبول طلباً مُسلّماً بالحالة الحالية وآخر بالقيمة القديمة: عكس الدفعة وإعادة تحصيلها مع إعادة إرسال متزامنة، ومنع التحصيل الزائد، وحفظ حدث التسليم الأصلي كما هو. لا يعيد التصحيح أو التحصيل تنفيذ التسليم.

### قبول ترقية بيانات قديمة والرجوع

بعد بناء التطبيق، شغّل `npm run test:upgrade-rollback -- --container <disposable-postgres-container> --rollback-image sultan-release:bc216ce` على Linux. يقبل المشغل قاعدة PostgreSQL على العنوان المحلي فقط، ويتأكد أن الحاوية المحددة هي الخدمة نفسها؛ ينشئ قواعد بأسماء عشوائية خاصة به ويحذفها بعد القبول. تستخدم كل السيناريوهات بيانات اصطناعية، ولا تُعد اعتماداً لأرصدة التشغيل القديمة.

يفحص ترقية المخطط الأول ببيانات مالية وحساب وتاريخ قديم إلى المخطط الحالي، ودقة `DECIMAL(14,2)` وحفظ السجلات وهوية الحساب وتاريخ التدقيق، ثم الدخول وقراءة الطلب من التطبيق. يجرّب فرقاً مالياً مقصوداً، ويتحقق من رفض SQL للسبب المحدد ومن توقف مشغل الترحيل في الترحيل المالي دون تعديل البيانات أو ترك مخطط جزئي، ثم يصالح البيانات الاصطناعية ويعيد الترقية. قد يعرض Prisma خطأ معاملة متوقفة بدلاً من الاستثناء المالي الأصلي؛ لذلك يُفحص السبب مباشرة من SQL أيضاً.

يفحص السيناريو الأخير صورة الإصدار السابق فعلياً على المخطط السادس، ثم التطبيق المرشح بعد الترقية، ثم إيقاف المرشح واستعادة نسخة مشفرة للمخطط السادس وتشغيل الصورة السابقة عليها؛ يشمل القبول تسجيل الدخول وقراءة أرصدة الطلب، وحفظ الحساب وسجل التدقيق. `--database-only` يفحص سيناريوهات قواعد البيانات فقط ويصرّح صراحة بأن قبول الرجوع إلى تشغيل الإصدار السابق غير مكتمل. يجمع `scripts/verify-cloud-build.sh` القبول الكامل عند تمرير صورة الإصدار السابق كوسيط ثانٍ.

## النسخ الاحتياطي والاستعادة

`/api/settings/backup` ينزّل تصديرًا إداريًا JSON للاستخدام التشغيلي، ولا يُعد نسخة PostgreSQL كاملة قابلة للاستعادة. يستبعد التصدير تجزئات كلمات المرور ومفتاح WhatsApp. للنسخ والاستعادة استخدم الأداة المشفرة؛ فهي تستخدم AES-256-GCM وتتحقق من سلامة الملف قبل فحصه أو استعادته.

أنشئ مفتاحًا عشوائيًا مرة واحدة واحفظه في مدير أسرار؛ لا تضعه في Git أو بجانب النسخة:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

بعد ضبط `DB_BACKUP_ENCRYPTION_KEY` في البيئة، أنشئ النسخة المحلية. يدعم الأمر `pg_dump` المثبت على الجهاز أو حاوية PostgreSQL عبر `--container`:

```bash
npm run db:backup:encrypted -- create --container sultan-postgres-db
```

تحقق من المصادقة وفهرس PostgreSQL قبل نقل الملف المشفر إلى مخزن خارجي معتمد:

```bash
npm run db:backup:encrypted -- verify --file local-backups/اسم-النسخة.dump.aesgcm --container sultan-postgres-db
```

يمكن تجربة الاستعادة في قاعدة معزولة جديدة فقط. يتطلب الأمر `--apply` واسم قاعدة ينتهي بـ`_restore` أو `_restore_test`، ويرفض إعادة استخدام قاعدة موجودة:

```bash
npm run db:backup:encrypted -- restore --file local-backups/اسم-النسخة.dump.aesgcm --container sultan-postgres-db --target-db sultan_restore_test --apply
```

لاختبار إنشاء النسخة وتشفيرها والتحقق منها واستعادتها ثم حذف قاعدة الاختبار تلقائيًا، شغّل الاختبار الذاتي على قاعدة محلية فقط:

```bash
npm run db:backup:encrypted -- self-test --container sultan-postgres-db
```

لاختبار مسار أوسع على قاعدة مؤقتة اصطناعية، شغّل `npm run build` أولًا ثم:

```bash
npm run test:restore-start
```

ينشئ الاختبار قاعدة محلية مؤقتة، يطبق الترحيلات ويضيف طلبًا ودفعة اصطناعيين متطابقين، ثم ينشئ نسخة مشفرة ويستعيدها إلى قاعدة معزولة ويشغّل التطبيق عليها حتى ينجح فحص `/api/health`. يحذف قواعد الاختبار والنسخة المشفرة بعد الانتهاء. يحتاج Docker وحاوية PostgreSQL المحلية `sultan-postgres-db` وصلاحية `CREATEDB`؛ يمكن اختيار حاوية أخرى عبر `--container <name>`. يرفض الاتصال بأي مضيف قاعدة بيانات غير loopback.

الأداة تنشئ نسخة مشفرة محلية فقط؛ يجب نقلها إلى تخزين خارج الخادم وتطبيق سياسة احتفاظ يحددها المشغل. لا تحفظ مفتاح التشفير في موقع النسخة نفسه.

تشغّل فحوص Playwright العامة على نسخة الإنتاج المبنية عبر المنفذ `4317`:

```bash
npm run test:e2e
```

لتشغيل اختبارات الأدوار وعزل المنشآت والدفعات والتزامن وإعادة مزامنة الطلبات والتأكيدات على بيانات اصطناعية، استخدم:

```bash
npm run test:e2e:isolated
```

ينشئ المشغّل قاعدة PostgreSQL مؤقتة باسم عشوائي على `localhost` فقط، ويطبق الترحيلات ويزرع حسابات وطلبات اختبار، ثم يشغّل اختبارات المتصفح ويطلق تحديثي حالة متزامنين على PostgreSQL الفعلية للتحقق من نجاح تحديث واحد فقط ومن تسجيله مرة واحدة في سجل التدقيق. تتضمن اختبارات المتصفح فصل الشبكة، وحفظ الطلب في IndexedDB، وإغلاق الصفحة وإعادة فتح مسارها دون اتصال؛ يعرض عامل الخدمة صفحة احتياطية عامة فقط، ثم يعيد تحميل التطبيق عند عودة الشبكة ليتحقق الاختبار من مزامنة الطلب مرة واحدة. يخزّن العامل الصفحة الاحتياطية وحدها ولا يخزّن صفحات الحساب أو بيانات API. الاختبار يثبت المسار على Chrome المكتبي ولا يغني عن قبول جهاز Android أو iOS حقيقي. يحذف القاعدة بعد انتهاء الفحوص. يتطلب صلاحية PostgreSQL `CREATEDB` ونسخة التطبيق المبنية؛ ويرفض الاتصال بأي مضيف قاعدة بيانات غير محلي.

إذا كان متصفح Chromium الخاص بـ Playwright غير مثبت وكان Chrome مثبتًا، مرر مسار `chrome.exe` إلى متغير `E2E_CHROME_PATH` قبل تشغيل الفحوص.

إعداد Capacitor الحالي يشير إلى مجلد `out`، بينما التطبيق يعتمد على API وجلسات وقاعدة بيانات ديناميكية. لذلك لا يُعد هذا الإعداد حاليًا مسار بناء موبايل مستقلًا؛ يلزم تصميم اتصال آمن بخادم منشور قبل تفعيله.
